# MickHub: contexto para Claude

Cliente de git de escritorio a la medida del dueño, para reemplazar a GitHub Desktop en su uso diario. Repo **público** en `github.com/Mickaell22/mickhub`, licencia MIT. El dueño es mickaell; las reglas generales (sin emojis, commits solo con permiso, nunca trailers de autoría, no hardcodear) viven en su CLAUDE.md global y mandan sobre todo.

Proyecto hermano: **Surco** (`../Surco`), su reproductor de música en Flutter. MickHub hereda de ahí el flujo de trabajo, el estilo de README y la idea de temas y decoraciones, pero mucho más cargada. Antes de reinventar algo de temas, paletas aleatorias, temporadas o `CustomPainter`, mirar cómo lo resolvió Surco (`lib/settings.dart`, `lib/theme.dart`, `lib/ui/decor.dart`) y sus trampas en `../Surco/CLAUDE.md`.

Estado: **v1 en curso**. `app/` (org `com.mickaell`, plataformas windows, linux y android) ya tiene la vista principal al estilo de GitHub Desktop: barra con repositorio, rama y fetch/pull/push; tabs Cambios (casillas, commit, diff) e Historial; clonado desde la lista de repos de GitHub. También: candado de cambios locales (con sección "Protegidos" y aviso si un pull choca), descartar cambios con papelera propia, apartados (stash por archivos con nombre), nueva rama local, búsqueda en historial, grupos de repos con ícono, abrir carpeta/editor, menús contextuales con íconos, ícono propio, cuentas con estado de sesión, fotos de GitHub de cada autor, acciones sobre commits hechos (copiar hash, ver en la web, revertir, deshacer el último sin subir), firma de commits por cuenta, login cuando la sesión vence, lista de repos de Azure al clonar, historial paginado con búsqueda en todo el historial, conflictos de pull (usar mi versión / la del remoto / corregir, terminar o abortar merge o rebase), apartar bloques sueltos de un archivo, repos nuevos y publicarlos (GitHub o un proyecto de Azure), selector nativo de carpetas, atajos de teclado, papelera que se vacía sola, actualizador integrado y abrir en el editor el repo junto con el archivo seleccionado (en VS Code/Cursor/Codium, en la línea del primer cambio o conflicto). **v2 empezada**: resúmenes de commits con IA (`api/` + `summaries.dart`), ver abajo.

## Diseño base: copia de GitHub Desktop

El layout y los colores salen de GitHub Desktop 3.4 (MIT), sacados con ingeniería inversa de sus SCSS originales: vienen enteros en `sourcesContent` de `resources/app/renderer.css.map` (en Kali: `/usr/lib/github-desktop/resources/app/`). Para medir algo nuevo, extraer de ahí en vez de adivinar; `themes/_dark.scss` y `_variables.scss` tienen casi todo. Los valores ya resueltos (darken/lighten de Sass pasados a hex) viven en `app/lib/theme.dart` (`Gh`) y los de sintaxis en `app/lib/syntax.dart`. Esta es la **base**; la personalización (temas, decoraciones) va encima y no debe romper estas medidas.

Mapa de `app/lib/`: `main.dart` (ventana, barra, desplegables, menú de repos, grupos), `panes.dart` (Cambios e Historial), `diff_view.dart` (parser y visor de diff), `syntax.dart` (resaltado con el paquete `highlight`), `git.dart` (todo lo que llama a git), `github.dart` (API de GitHub), `clone_dialog.dart`, `settings.dart`, `theme.dart`, `system.dart` (abrir carpeta/editor), `trash.dart` (papelera), `avatar.dart` (fotos: `avatars.githubusercontent.com/u/e?email=` como hace Desktop; email desconocido = identicon de GitHub; sin red = iniciales), `accounts.dart` (cuentas, sesiones, API de Azure), `accounts_ui.dart` (sus diálogos), `repo_dialogs.dart` (nuevo repo y publicar), `updater.dart` (actualizador), `change_groups.dart`/`change_groups_ui.dart` (grupos de cambios), `summaries.dart` (cliente de la API de resúmenes), `summaries_pane.dart` (pestaña Resúmenes; el comando `mickhub` vive aparte en `cli/`) e `image_diff.dart` (imágenes antes/después: git las marca binarias; sus bytes se leen con `blobAt`, que no pasa por texto como `git()`).

Ícono: original (una "M" hecha de grafo de commits), generado por `app/tool/icon.py` (Pillow) en `app/assets/icon.png`; de ahí salen con ImageMagick el `.ico` de Windows y los mipmaps de Android. En Linux lo pone `linux/runner/my_application.cc` escalado a 128 px: a 1024 px no entra en `_NET_WM_ICON` de X11 y la barra de tareas muestra el genérico sin dar error.

Flujo "fix rápido" (pedido explícito del dueño): con una implementación a medias en su rama, **Apartar** los archivos que no deben viajar (`git stash push --include-untracked -m <nombre> -- <rutas>`), crear **Nueva rama local** (los cambios sin commitear que quedan viajan con ella), hacer el fix, volver y **Recuperar** (`stash pop`). Los stashes de GitHub Desktop (`!!GitHub_Desktop<rama>`) aparecen como "Guardado por GitHub Desktop". **Papelera**: antes de descartar se copia el archivo a `<dir de ajustes>/papelera/<timestamp>/` (`contenido` + `meta.json`); al abrir la app se borra lo más viejo que `trashDays` (30 por defecto).

**Cuentas**: una cuenta es una **identidad** (nombre/email con que firma) que puede tener a la vez un usuario de GitHub y una o varias organizaciones de Azure DevOps (`Target`s). Caso real del dueño: su cuenta del trabajo es un GitHub del trabajo, pero los repos de la empresa están en Azure DevOps; la personal es su GitHub. Cada `Target` tiene su propia credencial y sesión. La cuenta de un repo sale de su remoto (`accountFor`: organización de Azure en `azureOrgs`; en GitHub, usuario embebido en la URL o dueño igual a `githubUser`; con una sola cuenta con GitHub, esa) o se fuerza con clic derecho en el repo (`repoAccounts`). Los commits y pulls van con `git -c user.name=… -c user.email=…`: no se toca la config del repo, así que un commit hecho fuera de MickHub usa la config normal de git. La sesión se verifica pidiendo la credencial con `GCM_INTERACTIVE=never` (sin ventanas) y probándola contra la API (`/user` de GitHub, `profiles/me` de Azure; Azure acepta Bearer u OAuth y devuelve 203 con HTML o redirige al login cuando no autoriza). Si un fetch/pull/push falla por autenticación (`isAuthError`), se ofrece "Iniciar sesión": `credential reject` de la vencida, `credential fill` interactivo (el GCM abre su login) y `credential approve`, y se reintenta. Con `gh` como helper (Linux) no hay login con ventana: MickHub muestra el comando `gh auth login … && gh auth switch -u <cuenta activa>` listo para copiar. **gh con varias cuentas**: `gh auth git-credential` entrega siempre la cuenta *activa* e ignora el usuario pedido, así que el token de una cuenta concreta se pide con `gh auth token --user <login>` (gh distingue mayúsculas; el login exacto sale de `gh auth status --json hosts`) y a git se le pasa en `GH_TOKEN` (`gitAuthEnv`), que gh respeta. **Azure**: la sesión se verifica contra la organización (`dev.azure.com/<org>/_apis/connectionData`), no contra el servicio de perfiles, que rechaza tokens válidos de empresas con acceso condicional; ojo que sin token esa URL responde 200 con un usuario anónimo (`PublicAccess`). En Linux el GCM necesita `credential.credentialStore` (en este Kali: `secretservice`, el llavero de GNOME).

**Gotcha**: nunca poner un `PopupMenuButton` (ni nada que abra una ruta con su propio context) dentro del panel desplegable de repos/ramas si la opción elegida cierra el panel: el menú queda colgado de un widget desmontado y Flutter falla con `'_dependents.isEmpty'` (pantalla roja). Abrir esos menús con `showMenu(context: <context del Shell>)`, como `_addMenu`.

**Grupos de cambios** (`change_groups.dart`, como las changelists de JetBrains; pedido del dueño para no apartar/ocultar archivo por archivo): los cambios de un repo se reparten por tarea. Se guardan en `<.git>/mickhub/grupos.json` (local, nunca se sube): `groups` (orden), `active` (grupo donde cae lo nuevo que se toca), `files` (ruta -> grupo; `''` = sin grupo **a propósito**, para que el activo no se lleve lo que ya estaba), `hunks` (ruta -> clave de bloque -> grupo, solo archivos repartidos) y `collapsed`. **Las asignaciones se recuerdan mientras el archivo siga con cambios, apartado o protegido** (pedido del dueño: cambió de rama en GitHub Desktop, que aparta solo, y perdió los grupos). `reconcile` (`change_groups.dart`) = `sync` + `prune`: olvida lo que no está en `status`, ni en ningún stash (los de Desktop incluidos), ni protegido. Lo corren la app y `mickhub` tras commitear, apartar y recuperar, y `mickhub estado` antes de mostrar, así CLI y app calculan lo mismo (antes `files` llegó a 47 rutas viejas y el CLI mostraba en "Sin grupo" lo que la app ponía en el activo). `forget` olvida al commitear o descartar desde MickHub. Por lotes: Ctrl/Shift+clic eligen varias filas (`_picked`) y el clic derecho sobre la selección mueve, aparta, protege o descarta todas; cada grupo tiene "Descartar grupo" (`discardHunks` para sus bloques en archivos repartidos). Un archivo repartido aparece en cada grupo con solo sus bloques; las claves de bloque son un hash de sus líneas `+`/`-` (`hunkKeys`), así siguen en su grupo aunque cambien de línea. Commit de un grupo con archivos repartidos: `commit(partial:)` hace `git apply --cached` con solo esos bloques. "Apartar grupo" usa `shelveParts` (archivos enteros + bloques en un solo stash, con el nombre del grupo); al recuperarlo, sus archivos vuelven solos a su grupo, con su reparto por bloque, porque la asignación se recuerda. Sin grupos definidos la lista se ve plana como antes y no se escribe ningún JSON. Los **protegidos** siguen recordando su grupo (proteger no llama a `forget`), así que la sección Protegidos los agrupa con "Desproteger grupo" y al desprotegerlos vuelven a su grupo. **Proteger un grupo** lo marca en `protectedGroups` (pedido del dueño, 17/11/2026): lo que entre después (grupo activo, `mover`, lo que edita una sesión) se protege solo (`protectJoined`, en `reconcile` y en el `_load` de la app); desproteger un archivo suelto de ese grupo lo saca a "Sin grupo" (si no, se volvería a proteger solo); `mickhub commit` se niega a commitear un grupo protegido. Los archivos repartidos con otro grupo no se protegen (skip-worktree es por archivo entero); los **apartados** muestran de qué grupos son sus archivos y, al apartar varios de un mismo grupo, el nombre sugerido es el del grupo. Claude Code puede crear/mover grupos editando ese JSON (escritura atómica) y apretando refrescar (F5) en la app.

**Gotcha de diálogos**: no hacer `controller.dispose()` apenas vuelve `showDialog`: el campo todavía lo usa en la animación de cierre y, si algo reconstruye el diálogo, Flutter falla con `'_dependents.isEmpty'`. Usar `disposeAfterDialog` (theme.dart) o que el diálogo sea un `StatefulWidget` dueño de su controlador (`_NameDialog`). **Apartar y recuperar (incidente del 17/11/2026)**: `git stash push -- <rutas>` guarda el índice ENTERO; un archivo nuevo de otro grupo añadido al índice se colaba en el apartado y al recuperar fallaba con "already exists", dejando todo a medias. Por eso `shelve` hace `git reset -q` antes (MickHub no usa el stage: el commit también lo vacía) y `unshelve` ya no usa `stash pop`: decide archivo por archivo (igual -> se salta; sin cambios y misma base -> se escribe; si no, su parte como parche) y es **todo o nada**: si uno choca no toca ninguno y lo nombra. Lee con `cat-file --filters` para respetar CRLF en Windows. Cada apartado que se recupera o elimina deja su commit en `refs/mickhub/respaldos/<ms>` (últimos 50; `git stash store` lo devuelve). `shelveGrouped`/`unshelveGrouped` anotan en `shelved` (hash del stash -> ruta -> grupo) y devuelven cada archivo a su grupo. `protect` saca el archivo del stage y usa skip-worktree solo si está en HEAD (antes, un nuevo añadido al índice quedaba ahí y un `git commit` lo subía).

**Apartar bloques** (`shelveHunks`): arma un parche con los bloques `@@` elegidos, deja el archivo como HEAD + esos bloques, hace `stash push` de ese archivo y reescribe el archivo con el resto; si algo falla, restaura el original (y antes guarda copia en la papelera). Al recuperar, si el archivo tiene otros cambios `stash pop` se niega, así que `unshelve` aplica `stash show -p` como parche y luego hace `drop`. **Conflictos**: en un rebase git invierte ours/theirs; `resolveWith(mine:)` lo corrige según `mergeState`. **Pull con cambios sin commitear en los mismos archivos** (caso real del dueño en el trabajo): git se niega ("would be overwritten by merge"); `pullBlockedBy` lo detecta y MickHub ofrece `pull --autostash` (como Desktop: aparta, trae y vuelve a poner). Si chocan en las mismas líneas queda `MergeState.stash`: sin MERGE_HEAD, solo archivos en conflicto, ours/theirs invertidos como en un rebase, sin "Abortar" (la copia sigue en el apartado "autostash") y "Listo" saca los archivos del stage y borra ese apartado. `pull()` pasa `--no-rebase` si el usuario no configuró `pull.rebase`: sin eso git falla con "divergent branches" cuando hay commits para subir y para traer.

**Release**: subir un tag `vX.Y.Z` dispara `.github/workflows/release.yml`, que compila Linux (ubuntu) y Windows (windows-latest, no se puede compilar desde Linux) y crea el release con `mickhub-linux-x64.tar.gz`, `mickhub-windows-x64.zip` y `SHA256SUMS.txt`. Ejecutables **portables**, sin instalador (pedido explícito: el instalador puede no estar permitido en las máquinas del trabajo). Nombres sin versión, como Surco, para que los links `releases/latest/download/...` del README no se rompan. La versión de Flutter del workflow (`FLUTTER_VERSION`) debe seguir a la local.

**Actualizador** (`updater.dart`): el workflow compila con `--dart-define=MICKHUB_VERSION=<tag>` y `MICKHUB_REPO=<owner/repo>`; sin esos defines (build local) queda apagado. Al abrir consulta `releases/latest`; si hay una versión mayor muestra un botón en la barra. Descarga el paquete de su plataforma, lo verifica contra `SHA256SUMS.txt` (si no coincide no toca nada), lo descomprime y deja un script desacoplado que espera a que la app cierre, copia encima de la carpeta del ejecutable y la reabre. Si esa carpeta no es escribible, avisa que hay que descargarla a mano. Por eso el release **siempre** debe traer `SHA256SUMS.txt` y los nombres fijos de los paquetes.

Optimización ya hecha: el resaltado del diff corre en un isolate (`Isolate.run`); diffs de más de 1 MB se ocultan hasta pedirlos; los remotos de los repos se leen en paralelo al arrancar. La lista de repos y la barra salen de una sola llamada por repo (`git status --porcelain=v2 --branch`, `repoSummary`): rama, ↓↑ y cantidad de cambios. Fetch en segundo plano (`backgroundFetch`, con `GCM_INTERACTIVE=never` para no abrir logins) al abrir, cada 10 min y al volver a la ventana; a lo sumo 3 a la vez. Cambios lee git en paralelo y guarda lo último de cada repo para mostrarlo al instante al volver. Los `git status` van con `GIT_OPTIONAL_LOCKS=0` (`readOnly`), como Desktop: si no, toman un momento `.git/index.lock` y chocan con un commit o cambio de rama hecho a la vez en Desktop o la terminal. Las fotos se guardan en `<dir de ajustes>/fotos/` (nombre = sha1 de la URL) y se renuevan cada 7 días.

**Resúmenes con IA (v2)**: `api/main.py` (FastAPI, un solo archivo) guarda en la tabla `summaries` un resumen por **hash** (clave primaria): `POST /summaries` devuelve el existente o llama a DeepSeek (SDK `anthropic` contra `https://api.deepseek.com/anthropic`, como mcp-context); `GET /summaries/{hash}` (404 si no hay) y `GET /summaries?q=&repo=&author=` (búsqueda). Auth: `Authorization: Bearer <MICKHUB_API_TOKEN>`. La app (`SummaryApi`) primero hace GET, así un commit ya resumido no manda su diff; solo si da 404 lee `git show` y hace POST. Se pide **al abrir el commit** (decisión del dueño: gastar tokens solo en lo que mira). Los merges (2+ padres) se guardan con su primera línea, sin IA. El diff se corta en `MAX_DIFF_CHARS` (`truncated` lo marca). El repo se identifica con `repoId` (remoto sin esquema, credenciales ni `.git`), igual en todos los equipos. El prompt dice "describe, no revises": sin eso DeepSeek se ponía a señalar bugs. `DEEPSEEK_MAX_TOKENS` no puede ser chico: en los modelos v4 el razonamiento sale de ahí y la respuesta llega vacía. Producción: proyecto Railway **MickHub** (servicio `api` + Postgres). Desde el 21/11/2026 el servicio está **conectado al repo de GitHub** (rama `main`, carpeta raíz `/api`, solo despliega si cambia `/api/**`): cada push que toca la API va directo a producción. El comando de arranque y el healthcheck están en la configuración del servicio (Railway rechaza `railwayConfigFile`: dice que config-as-code está deprecado), no solo en `railway.json`. `railway up` desde `api/` sigue sirviendo para probar algo sin commitear; `.railwayignore` deja fuera `.env` y `.venv`. **Modo local** (como en mcp-context: mismo código, sin flag de modo; solo cambia a dónde apunta `DATABASE_URL`): API en `127.0.0.1:8765` con `uvicorn --env-file .env` y una Postgres local; la tabla la crea `lifespan` al arrancar. Guía para Claude en `docs/INSTALACION.md` (local con systemd de usuario o tarea de Windows, o nube). Verificado el 2026-11-17 con una Postgres 17 vacía: `/health`, 401 sin token y un resumen de merge guardado. En local cada equipo tiene sus propios resúmenes. **Commits partidos** ("avance" + "final" en días distintos, pedido del dueño): `relatedCommits` (git.dart) busca el anterior y el siguiente del mismo autor, sin merges, a menos de `relatedDays` (7) días y con Jaccard de archivos ≥ 0.5 (no "mín. de los dos": un commit de un solo archivo pasaba como pariente de cualquiera que lo tocara); el Historial los muestra como "Continúa a… / Sigue en…" clicables. Es git local, sin IA. Medido en este repo: ~9 de 20 commits enlazados (commits grandes que tocan main/panes, y releases entre sí); si molesta, exigir además que uno de los mensajes sea vago. La pestaña **Resúmenes** (tercera, Ctrl+3, solo si la API está configurada) usa `GET /summaries`: "Este repo" filtra por `repoId`, "Todos" sin filtro; pagina de a 50. "Resumir los últimos 50" recorre la rama de a 3 en paralelo con el mismo `summary()` (lo ya resumido solo se consulta) y se puede cancelar; la app manda como mucho 200 000 caracteres de diff (`_maxDiffSent`). Medido: los 22 commits de este repo en 33 s, ~0,04 USD. **Mensaje del commit con IA** (como Copilot): botón con chispas en el campo Resumen de Cambios; pregunta "¿Qué hiciste? (opcional)" (`askCommitHint`, prellenado con lo escrito en Resumen) y manda a `POST /commit-message` solo el diff de **lo marcado** (`_marked()`: archivos enteros con `fileDiff` y bloques de repartidos con `selectHunks`) más los últimos 15 mensajes del repo para copiar su estilo; no guarda nada en la base. **Reporte del período** (botón en Resúmenes; `POST /report`, sin guardar nada): elige período (`ReportPeriod`: hoy, ayer, esta semana desde el lunes, la pasada, 30 días; hasta excluido y días con `DateTime(y, m, d - n)` por el cambio de horario), mis commits o del equipo, este repo o todos los del perfil. Los commits salen de `periodCommits` (`log --branches --remotes --tags --no-merges`; no `--all`: trae los stashes y el commit del índice de un stash no es merge) con `--author` por cada identidad de la cuenta del repo (nombre, email, usuario de GitHub, `-i --fixed-strings`); un repo sin cuenta no entra en "mis commits". Los que falten se resumen con el mismo `summary()` de a 3 y la API arma el reporte con los resúmenes ordenados por autor; si no entran en `REPORT_MAX_CHARS` va solo la primera línea de cada uno, y si ni así, se cortan los más viejos (cortar en orden de autor dejaba fuera a los últimos del abecedario). **Lo que trae la rama** es el mismo reporte con `branchCommits` (`<base>..HEAD --no-merges`): lo que entró al ponerla al día con la base ya está en la base y no cuenta, sea merge, rebase o fast-forward; la base por defecto es `origin/HEAD`. Probado el 21/11/2026 contra los repos del trabajo, solo lectura (91 commits de 10 personas en 5 repos: ~40 s, front y back del mismo trabajo en una viñeta). **Los repos del trabajo son solo para mirar** (dueño): nada de pruebas que escriban en ellos; las pruebas van en repos temporales o en este. **Archivos que no son UTF-8** (Latin-1 / Windows-1252 en los backends del trabajo): `git()` fallaba con `FormatException` y Cambios no mostraba el diff. Ahora la salida pasa por `decodeGit`, que deja cada byte inválido como U+DC80+byte (el "surrogateescape" de Python), y lo que vuelve a git (stdin, archivos de parche) pasa por `encodeGit`, que lo devuelve al mismo byte: un commit parcial, descartar o apartar bloques escriben los bytes exactos (`encoding_test.dart`). Para mostrar o mandar a la IA, `readable` los pasa a Windows-1252; nunca mandar a git un texto pasado por `readable`. `hunkKeys` hashea con `encodeGit` para que dos líneas Latin-1 distintas no den la misma clave. En el mismo test salió que `selectHunks` hacía `trimRight()` y se comía el `\r` final en archivos CRLF guardados así en el repo (típico en .NET): el parche no calzaba. **Tests con muchos commits**: git 2.5x empaqueta en segundo plano tras ~100 objetos sueltos y leer a la vez falla con "Could not read <objeto>"; el `tempRepo` de `workflow_test` apaga `maintenance.auto` y `gc.auto`. "Ver en el Historial" en un resumen abre su repo (por `repoId`) y el commit, aunque no esté en la rama (`commitByHash`). Las releases (`isRelease`: `chore(release):`, `v1.2.3`...) no se enlazan como "avance/final": todas tocan el pubspec. Falta: la vista de celular.

## Operar MickHub desde Claude Code

El dueño quiere poder pedirle a Claude "clóname X", "agrupa estos repos", etc. No hay API para esto a propósito: todo el estado de la app es git más un JSON, y la app **vigila ese JSON y se recarga sola** (`Settings.watch`), así que basta con:

- **Ajustes**: `~mickaell/.local/share/com.mickaell.mickhub/settings.json` (en Windows, `%APPDATA%\com.mickaell\mickhub\settings.json`). Claves: `reposDir` (carpeta de clonado; sus subcarpetas con `.git` aparecen solas), `extraRepos` (rutas fuera de `reposDir`), `groups` (ruta absoluta del repo -> nombre de grupo), `accounts` (lista: `id`, `label`, `githubUser`, `azureOrgs`, `gitName`, `gitEmail`; el formato viejo con `provider`/`org`/`username` se convierte solo al leer), `repoAccounts` (ruta -> id de cuenta forzada), `groupIcons` (nombre de grupo -> clave de ícono de `groupIcons` en `theme.dart`; un grupo existe aunque no tenga repos), `currentRepo`, `sidebarWidth`, `editorCommand`, `trashDays` (días que dura la papelera), `terminalCommand` (terminal para "Abrir en la terminal"; vacío = la de `$TERMINAL` o la primera conocida instalada; en Windows `wt` o `cmd`), `collapsedGroups` (grupos contraídos en la lista; `''` = sin grupo), `groupFilter` (grupos marcados en el filtro; vacío = todos), `apiUrl` y `apiToken` (API de resúmenes; vacíos = apagada), `look` (paleta, nombre de `Look`), `rotation` (`fija`, `dia`, `abrir`), `seasonal` (fechas especiales, por defecto sí), `skippedSeason`, `birthday` (`MM-DD`), `decor` (escenas y mascota), `scene` (`diaria` = una por día del año, de fábrica; `auto`, `ninguna` o nombre de `Scene`), `pet` (`ninguna`, `azar` o nombre de mascota), `profile` (perfil de la lista de repos: id de cuenta, `''` = todos; con dos cuentas o más aparece el selector arriba de la lista y muestra solo los repos de esa cuenta según `accountFor`, más los que no son de ninguna; los grupos con repos solo salen en el perfil donde los tienen; Clonar arranca en la cuenta del perfil), `profileDirs` (id de cuenta -> carpeta de clonado propia, p. ej. los repos del trabajo aparte; sin entrada, `reposDir`; lo clonado ahí entra por `extraRepos`; cambiar la carpeta en Clonar la guarda para la cuenta elegida). Editar como `mickaell` y escribir atómico (archivo temporal + rename); conservar las claves que no se tocan.
- **Clonar**: `git clone <url> "<reposDir>/<nombre>"` como `mickaell`. Si va a un grupo, agregar su ruta en `groups`.
- Las rutas de `groups` deben ser exactas: `<reposDir sin barra final>/<carpeta>`.

**Commits y push de Claude Code: siempre por `mickhub`** (pedido del dueño: que toda la actividad de git de Claude pase por MickHub y que varias sesiones a la vez no se mezclen). `cli/bin/mickhub.dart` es un ejecutable de Dart puro que reusa `git.dart`, `change_groups.dart` y `accounts.dart` (paquete aparte porque las dependencias de Flutter traen build hooks que `dart compile` no acepta; se instala con `cd cli && dart pub get && dart compile exe bin/mickhub.dart -o ~/.local/bin/mickhub`). Lo obligatorio no es una regla escrita sino **hooks de Claude Code** en `~/.claude/settings.json` (`PreToolUse` y `PostToolUse` sobre `Bash|Edit|Write|MultiEdit|NotebookEdit` -> `mickhub hook`):
- Antes de un Bash con `git commit`/`git push` (también con `-C` o `cd` a otro repo) en un repo de la lista de MickHub (`reposDir` + `extraRepos`), sale con código 2 y le dice a Claude que use `mickhub commit`/`mickhub push`. Fuera de esos repos no toca nada.
- Cada sesión (`session_id`, que en los comandos llega como `CLAUDE_CODE_SESSION_ID`) tiene su grupo en `sessions` de `grupos.json` ("Sesión e384" hasta que Claude lo nombra con `mickhub grupo "<tarea>"`; si el nombre ya existe, se une). Antes de editar se guarda una foto de las claves de bloque (`<.git>/mickhub/sesiones/<sesión>.json`); después, lo que no estaba en la foto es de esa sesión (`ChangeGroups.claim`). Así, si dos sesiones (o el dueño) tocan el mismo archivo, cada una se queda con sus bloques. En un Bash la foto es de todo el repo (cubre `sed`, formateadores...); con más de 300 archivos cambiados no se reparte.
- `mickhub commit -m ... [-m ...]` commitea solo el grupo de la sesión (archivos enteros y bloques sueltos), firmado con la cuenta del repo, y rechaza mensajes con `Co-Authored-By`, `Generated with`, enlaces de claude.ai, etc. `mickhub push` usa el token de la cuenta (`gitAuthEnv`) y no sube si hay commits para traer; acepta args de `git push` (tags). También `estado`, `mover`, `pull`.
- **El grupo viaja con el commit** (pedido del dueño: al subir se perdía el agrupado y el grupo quedaba vacío): `commits` en `grupos.json` guarda hash -> grupo -> archivos, desde la app y desde `mickhub commit`. El Historial muestra la etiqueta del grupo en cada commit y agrupa por grupo la lista de archivos del commit; en Cambios, la cabecera de un grupo cuenta sus commits sin subir (`unpushedCommits`). Es local (no cruza equipos todavía; sería en la API).
- **Al commitear**, `ChangeGroups.committed` olvida lo commiteado y quita de la lista los grupos que quedaron sin cambios (pedido del dueño); su etiqueta en `commits` y su entrada en `sessions` quedan, así la sesión que vuelve a editar recupera el mismo nombre. En el Historial, los grupos de la lista de archivos de un commit se contraen con un clic (en memoria, siguen cerrados al cambiar de commit).
- **Abrir la sesión de un grupo** (clic derecho en la cabecera en Cambios, o en el commit en el Historial): `claude --resume <id>` en la terminal configurada, en la carpeta donde corría la sesión, que sale del primer `cwd` de su transcript (`~/.claude/projects/*/<id>.jsonl`, `claudeSessionDir`); sin esa carpeta, `--resume` no la encuentra. En Linux va por `$SHELL -lc` porque la app abierta desde el dock no tiene `~/.local/bin` en el PATH. Cada terminal recibe el comando distinto (`terminalRunArgs`). Los grupos no se sincronizan entre equipos a propósito (dueño: en otro equipo son otros cambios).
- **Push solo si el dueño lo pide** (regla suya: él sube a mano): el hook también corre en `UserPromptSubmit` y, si el mensaje trae una orden de subir ("haz push", "dale push", "commit y push", "súbelo", "sube lo de…", "en el repo de github"; no negada, `_asksPush`), deja una marca por sesión en `~/.cache/mickhub/push/` que vale para ese turno. Sin la marca, `git push` y `mickhub push` se bloquean en cualquier repo. Una palabra suelta no basta: "solo commit y no push" no da permiso, ni "sube la prioridad" o "revisa el código en github".
- **Nombres**: un grupo nuevo de sesión se llama "Sesión xxxx"; al crearlo, el hook `PostToolUse` le devuelve a Claude un `additionalContext` pidiéndole nombrarlo con `mickhub grupo`. Si llega al commit sin nombre, toma el del título del commit (sin el `tipo(ámbito): `).
- `mickhub` se reemplaza con rename (compilar a `.nuevo` y `mv`): los hooks lo están corriendo y escribir encima da "Text file busy". El release trae `mickhub-cli-linux-x64` y `mickhub-cli-windows-x64.exe` para el repo privado `claude-config`, que instala todo en cada equipo.
- El hook no reparte tras un Bash que solo mueve cambios existentes (`git stash/checkout/switch/restore/reset/pull/merge/rebase...` o `mickhub ...`, `_movesChanges`): antes, recuperar un apartado desde Claude dejaba todo en "Sesión xxxx". `_relative` conserva mayúsculas (en Windows las bajaba y `mover` guardaba una clave que no era la de git) y `mover` confirma releyendo el JSON. `UserPromptSubmit` no recorre la carpeta de repos, stdin tiene tope de 3 s y el proceso sale con `exit` explícito: con stdin abierto la VM no termina sola y Claude Code cortaba el hook a los 10 s (visto en Windows). `apartados`/`apartar`/`recuperar`/`protegidos`/`proteger`/`desproteger` existen para que desde la terminal se vea y arregle lo mismo que en la app.
- El mensaje del commit a medio escribir (el de la IA incluido) se guarda por repo en memoria (`_drafts` en `panes.dart`): el panel se destruye al cambiar de pestaña y se perdía.
- La app vigila `grupos.json` (`ChangeGroups.watch`) y se recarga sola. El candado `grupos.lock` es solo entre procesos de `mickhub`; la app guarda sin él (ponytail anotado en el código).

## Por qué existe (el problema real)

GitHub Desktop se le queda corto en:
- No está sincronizado con sus proyectos: clonar implica buscar la URL. Quiere ver la lista completa de sus repos, con filtros, y clonar con un clic.
- **Cambios locales que nunca deben subirse**: en el trabajo mueve o edita archivos para que el proyecto corra en local, y en cada commit tiene que revisarlos a mano para que no se cuelen. Quiere ocultarlos "sí o sí".
- **Historial ilegible**: él usa Conventional Commits, pero sus compañeros escriben cosas como "ajustes" con 5 archivos tocados. Quiere que una IA (DeepSeek, ya tiene API key) lea el diff y escriba qué se hizo de verdad, guardado y buscable.

## Cómo lo usa (define prioridades)

- **Celular (Android)**: solo para mirar (historial, resúmenes). Sin operaciones de git.
